# 0.1 正式版：可观测、可恢复的 DAG Agent Runtime

规划日期：2026-10-25。本文是后续开发的范围与验收基线，尚未实现的工作保持待办；完成规划不表示完成版本。

## 产品目标与版本定位

Synapse Runtime 面向自行部署的群聊助手维护者与 Agent 开发者，提供本地优先的执行服务：从真实消息开始，使用有来源的上下文调用模型与受控工具，交付可验证的结果，并能解释每一次运行。

**0.1 是范围收敛、体验完整的首个正式交付版本；1.0 是具备明确兼容承诺、持续运行能力和可重复发布流程的稳定产品目标。** 0.1 就确立核心数据模型、交互结构、安全边界、恢复语义与质量标准，后续版本在这些基础上增加能力。版本号较小不能成为缺少错误处理、历史查询、部署说明或真实验收的理由。

0.1 的完整用户旅程是：安装与配置 → 检查依赖 → 连接频道 → 发起任务 → 查看执行 → 获取工件与回复 → 排查失败 → 重启后检查记录 → 备份与升级。主场景仍为“在 NapCat 群聊中生成 XLSX 并交付群文件”，文本问答与后续读取历史结果是配套场景。

本轮交付仅为代码审计与实施计划，不改动 Runtime 行为，不创建新 WebUI，不执行真实群消息或上传动作。

## 与既有工作的关系

[旧工件 PRD](./v0.1-dag-artifacts-prd.md)已经实现 DAG 上下文、容器工件、群文件上传和副作用去重，其 `completed` 仅表示原范围的实现及当时自动化验收完成。它是本计划的基础能力记录，不是 0.1 正式发布凭据。

[代码审计](../reference/v0.1-code-audit.md)表明：目前有 LineEvent、EventProcessState、Run Ref 和工具回执，但缺少统一的持久 Run Trace；模型调用没有实时逐步持久化；Admin 没有 Run 查询接口；SSE 是内存日志流；仓库没有 `apps/webui`。这些均属于新增开发，不能通过改名或补文档算作完成。

## 0.1 必须确立的产品原则

| 原则           | 0.1 的具体承诺                                            | 1.0 的延续方式                             |
| -------------- | --------------------------------------------------------- | ------------------------------------------ |
| 运行是一级对象 | 接受任务时分配稳定 Run ID，所有事件、调用和结果可关联     | 后台任务和扩展 Agent 复用相同运行契约      |
| 数据各司其职   | Transcript 保存消息，DAG 保存语义结果，Trace 保存执行事实 | 通过引用演进，不以日志或图节点代替所有数据 |
| 结果以回执为准 | 生成、上传、回复分别展示；未知结果显式标记                | 自动化与人工处理都遵守相同副作用边界       |
| 默认受控       | 会话隔离、权限检查、容器限额、凭据脱敏                    | 扩展工具不能绕过授权和审计                 |
| 可恢复且可解释 | 重启保留记录；安全恢复和需人工核对有明确区别              | 增强调度时保持相同幂等与恢复语义           |
| 完整的使用体验 | 加载、空白、失败、断线、无权限、依赖缺失都有可执行指引    | 新功能进入既有信息结构与交互规范           |
| 可升级与可运维 | 版本化协议、迁移、备份恢复、容量限制、发布证据            | 1.0 冻结公开稳定面并建立支持周期           |

## 发布范围

以下 P0 全部阻断 0.1 正式发布，不以“先发布后补体验”降级。实现工作按后文工作包推进。

### P0-A：稳定运行标识与持久事件

- Runtime 接受规范化事件后、上下文和模型工作开始前创建 Run；幂等键使用已持久化的规范化事件身份，包含频道与会话作用域，不直接依赖平台裸消息 ID
- 一个逻辑 Run 可以包含多个 attempt；恢复不生成第二个逻辑 Run，命令路径与普通 Agent 路径都纳入追踪。忽略的消息保留触发诊断，不计入接受的 Run
- Run 最少保存 `id`、`sourceEventId`、`sessionId`、`channelId`、可选 `lineId/branchId/taskId`、状态、当前阶段、起止时间、结果摘要与结构化错误
- RunEvent 最少保存事件 ID、`runId`、`attemptId`、Run 内 `seq`、全局流游标、类型、协议版本、时间、耗时和脱敏载荷；通过 `modelCallId/toolCallId/artifactId/commitId` 关联详情
- SQLite 追加事件与更新 Run 投影在同一事务完成；事件有唯一约束，重试相同写入返回原事件，冲突载荷拒绝覆盖
- 全局流游标与单 Run 序号分别使用，避免两个 Run 的 `seq=1` 发生订阅冲突；发布通知发生在事务提交之后
- 保留已有 LineEvent、恢复状态和工件回执的职责，定义它们到 Trace 的映射和重启补齐机制，不引入两套互相独立的副作用判断
- 旧数据继续可读，旧运行不伪造不存在的模型详情；新增迁移必须幂等、失败回滚、拒绝未来版本

建议状态基线如下，PR-01 固化后由服务端维护，前端不得凭事件数量猜测终态：

| 状态          | 含义与转换边界                                                     |
| ------------- | ------------------------------------------------------------------ |
| `accepted`    | 已持久接受，尚未开始执行                                           |
| `running`     | 执行中；阶段另存为 context/model/tool/commit/upload/response 等    |
| `succeeded`   | 所需结果交付与最终回复均已确认，记录已持久化                       |
| `failed`      | 已知失败，保存失败阶段与是否允许安全重试；发送失败提示不改变该结论 |
| `blocked`     | 必需权限或能力不满足，未完成请求                                   |
| `uncertain`   | 外部动作已发起但缺少可靠回执，禁止自动重放                         |
| `interrupted` | 进程中断且无未决外部动作；保留检查点，只有已定义的安全步骤可继续   |

允许 `accepted → running → 终态`；启动恢复可以将遗留 `accepted/running` 归入 `interrupted/uncertain`，或根据已有可靠回执补齐成功记录。0.1 终态不可通过普通写 API 任意改写；不开放通用“重新运行”按钮。未提供可靠继续机制时，应显示中断与处理指引，不能承诺从任意模型 token 续跑。

### P0-B：端到端采集与准确结果语义

- 上下文记录实际使用的 Ref 头、Commit 列表、裁剪信息与输入快照，详情查询不能改为读取后来变化的当前 Ref
- 模型每轮记录开始、成功或失败，包含 Provider/模型标识、实际输入消息与工具定义的脱敏快照、输出、耗时及实际返回的 usage；缺失统计显示“未知”，截断显示原因
- 工具记录调用、参数、权限允许或拒绝、执行终态、复用回执与恢复阻断；参数解析失败、未知工具和调用上限也必须有事件
- 容器记录排队/启动、资源约束、超时、退出、清理和工件校验结果，不把原始脚本与全部日志写入 DAG 上下文
- 工件生成、上传请求、平台确认、上传失败与未知回执分别可见；返回工具函数成功不等于群文件上传成功
- 最终回复记录发送前状态与平台回执；文件已上传但回复失败显示两个事实，不能重新上传文件来补发回复
- 对必需事件或副作用前检查点落盘失败采用停止执行策略；副作用后持久化失败进入未决恢复流程，不自动重复动作
- 重试沿用稳定 Run ID 并区分 attempt；定义安全重试清单和次数上限，不能将所有异常统一重试

### P0-C：只读查询 API、可靠事件流与客户端

沿用 `apps/runtime` 的 Admin 宿主与认证，所有浏览器访问经 `packages/runtime-client`。以下为拟新增契约，尚不是可调用接口：

| 接口                                                        | 最小能力                                              |
| ----------------------------------------------------------- | ----------------------------------------------------- |
| `GET /admin/runs`                                           | 游标分页；状态、频道、Session、时间范围筛选；稳定排序 |
| `GET /admin/runs/:id`                                       | 状态、阶段、结果、错误、关联对象与协议版本            |
| `GET /admin/runs/:id/events`                                | 按 `afterSeq` 增量读取，限制页大小                    |
| `GET /admin/runs/:id/context`                               | 本次实际输入快照、来源与截断标记                      |
| `GET /admin/sessions`、`GET /admin/sessions/:id/transcript` | 可发现的会话列表与有界消息历史                        |
| `GET /admin/sessions/:id/refs`、`GET /admin/commits/:id`    | 作用域校验后的引用、父节点与详情                      |
| `GET /admin/artifacts`、`GET /admin/artifacts/:id`          | 按会话或 Run 筛选的元数据、交付状态                   |
| `GET /admin/artifacts/:id/content`                          | 授权下载已登记工件，校验归属、大小、普通文件与完整性  |
| `GET /admin/run-events/stream`                              | 持久事件的 SSE 订阅与断点补读                         |

保留现有 `/admin/events/stream` 的日志语义与 TUI 兼容性。新 SSE 使用持久全局游标：建立订阅时确定高水位、提供快照/历史补读，再接续增量，消除查询与订阅之间的漏事件窗口。客户端按 ID 去重，断线退避重连，支持 AbortSignal；过期游标返回明确的重新同步指令。服务端提供心跳、连接释放、积压上限和慢客户端断开机制。

新接口提供明确 DTO、结构化错误、参数校验和版本信息；列表不得一次返回全部载荷。客户端类型不得导入服务端实现。当前边界检查禁止 runtime-client 依赖任何工作区包，PR-01 优先在客户端定义公开 wire DTO、服务端显式映射并做契约测试；如果确需独立协议包，必须同时更新边界规则和设计说明。

### P0-D：可日常使用的 WebUI

新增 `apps/webui`，按原提案采用 Vite、React、TypeScript，消费 runtime-client。它是已有仓库的独立客户端应用；Runtime 不依赖 React，不增加第二套管理后端。

| 页面           | 用户能完成的工作                                                                     |
| -------------- | ------------------------------------------------------------------------------------ |
| 连接与首次使用 | 配置 Runtime 地址与令牌，区分未连接、认证失败、版本不兼容；看到下一步设置指引        |
| Overview       | 查看服务就绪、频道连接、活动任务、最近失败/未知结果、依赖与存储告警                  |
| Runs           | 筛选、分页、查看阶段和耗时；刷新保留筛选，支持直接打开 Run 链接                      |
| Run Detail     | 实时时间线；展开输入输出、权限、错误与回执；跳转上下文和工件；明确“生成”和“交付”状态 |
| Data Explorer  | 查询 Session/Transcript、Ref/Commit 父子关系、调用记录、工件和下载状态               |

所有页面包含加载、空态、失败、无权限、断线重连与已过期数据状态。断线时显示数据更新时间；缺失 usage 不能显示为零；大对象按需展开并截断；键盘可达、焦点可见、状态同时使用文字表达，窄屏可阅读。复用已有语言资源机制，至少完整提供中文文案，新增文案纳入 i18n 检查。

首版以安装产物携带 WebUI 静态资源并通过 Admin 宿主访问为交付目标，开发时使用代理；固定资源路径和单页路由回退，确保回退不会吞掉 `/admin` API 的 404。浏览器 Bearer 令牌默认仅保存在内存，不写 URL、日志或分析埋点；SSE 使用带认证头的 fetch。显式配置同源 Origin，不使用通配允许来源来解决连接问题。

新增 WebUI 与 API 不提供修改消息、编辑 Commit、重放副作用或任意创建任务的入口；现有 CLI/TUI 的配置与频道操作继续保留。

### P0-E：安全、容量和运行可靠性

- 认证、Origin、远程地址规则覆盖新 API、SSE 与下载；0.1 的管理令牌代表整实例管理员，Session 校验是资源归属约束，不宣称多租户授权
- 写入前对 Trace 字段递归脱敏并限制深度、长度和体积；覆盖嵌套参数、Authorization、URL 查询凭据、错误对象、模型回显和已配置秘密值。不要保存原始配置对象或全部环境变量
- 审计现有日志和 DAG/Transcript 的检查出口，避免绕开 Trace 脱敏；非文本二进制仅保存引用，脱敏内容标注不可用字段
- 制定单 Run deadline、模型/工具超时、最大排队量和实例并发上限；拥塞时明确拒绝或排队，避免无限积压。沿用串行工具循环
- 退出时停止接单、等待有界收尾、终止受控容器、关闭 SSE 和 SQLite；启动后扫描未决记录，状态不会永久卡在“运行中”
- 明确每个数据目录仅一个 Runtime 进程，增加重复启动拒绝及可恢复的锁处理
- 提供数据保留期、磁盘用量提示、事件载荷上限和归档/清理流程；删除工件保留墓碑与必要交付回执，不能因清理丢失去重依据
- 长对话在最终模型请求处有统一输入预算和输出预留；包含工具定义、历史、DAG、工具观察，超限有裁剪原因或明确错误，不伪造精确 token 使用量

### P0-F：安装、升级与正式交付

- 固定支持矩阵：Node.js 24、pnpm 9.15.0、Windows + Docker Desktop Linux 容器、Linux + Docker Engine；实际验证版本写入发布记录，其他组合不默认为受支持
- 提供无需真实凭据的首次启动与演示路径，以及有真实凭据的部署指南；依赖检查覆盖配置、原生 SQLite ABI、Docker、工件镜像、端口和数据目录
- 明确 0.1 交付形式为版本化源码发布与从该源码构建的 Runtime/TUI/WebUI 产物，配套固定依赖锁、工件镜像构建说明和校验信息；全仓库当前并非已验证的 npm 产品，不把 `npm install` 写成可用交付渠道
- 提供一致性备份和恢复步骤，包含 SQLite/WAL、工件与上传回执；未经验证不能仅复制运行中的数据库文件
- 升级前备份、迁移失败回滚；数据库升级后旧二进制不保证可读，回滚必须配套恢复升级前数据。保留旧配置与文本对话路径
- 发布必须有自动化、真实 Docker、真实模型与 NapCat、WebUI 浏览器验收四类独立证据，以及候选版本持续运行记录

## 暂不纳入 0.1

多 Agent 协作、分布式执行、多租户、通用 Workflow 图编辑器、任意后台任务与定时调度、通用插件/MCP 市场、浏览器自动化、完整向量记忆、权限审批工作流不作为本版前置条件。数据契约允许后续扩展，但不为这些方向提前搭建空实现。

现有 QQ Official 与文本对话继续回归；它们不承担 NapCat 群文件能力承诺。DAG 提供列表与父节点追溯即可，0.1 不需要图编辑器。人工核对未知交付不等于开放“标记成功”或“强制重放”接口。

## 主要风险与处理

| 风险                                       | 处理方式                                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------------------- |
| LineEvent、Trace、文件回执同时写入产生分歧 | 写前检查点优先；以原持久回执为恢复依据，建立可重复的 Trace 补齐流程，覆盖每个崩溃窗口 |
| 检查模型输入暴露凭据或占满磁盘             | 写入前脱敏、载荷限额、按需详情、保留策略；不把全量原始配置当作调试数据                |
| 浏览器接入改变 Admin 安全假设              | 显式 Origin、内存令牌、受保护的 fetch/SSE、无 URL 令牌、完整鉴权测试                  |
| 原运行 ID 和新契约不兼容                   | 稳定逻辑 ID 与历史/attempt 标识分别保存；旧数据不伪造补齐                             |
| 0.1 扩张为平台工程                         | 固定主用户旅程与九个工作包；新增能力进入后续版本，不替换 P0 质量工作                  |
| 真实账号、模型或平台不可用                 | 继续完成自动化与 Docker 验收，真实交付保留“待验证”，不以替身结果放行                  |
