# Synapse Runtime 主线 / 支线会话模型 PRD

## 1. 文档信息

- 产品名称：Synapse Runtime
- 功能名称：主线 / 支线会话管理
- 版本：v0.1
- 优先级：P0
- 状态：待开发

---

## 2. 背景

当前对话通常被处理为一段连续的消息历史。

当用户在对话中同时提出多个问题，或者 Agent 需要执行搜索、代码分析、文件处理等独立任务时，所有内容都会混合在同一上下文中，容易产生以下问题：

1. 主对话被工具调用和执行过程打断。
2. 不同任务之间的上下文相互污染。
3. 长时间任务难以恢复和追踪。
4. 支线任务完成后，结果难以自然回到主对话。
5. 无法清晰表达“当前正在聊什么”和“后台正在做什么”。

因此需要建立一套统一的会话结构：

> 规范化落库 → Session → 主线 / 支线 → Append Event → Task

---

## 3. 产品目标

本期需要实现：

1. 所有接收到的消息和系统事件均规范化落库。
2. 每个会话 Session 默认拥有一条主线。
3. 一个 Session 可以创建多条支线。
4. 主线与支线均采用 append-only 方式追加记录。
5. 支线可以绑定一个或多个 Task。
6. 支线完成后，可以将结果追加回主线。
7. 主线、支线和 Task 均可以恢复、查询和追踪。

---

## 4. 非目标

本期不实现：

1. 自动生成复杂的知识图谱。
2. 自动长期记忆提取。
3. 跨 Session 自动合并话题。
4. 支线之间的嵌套支线。
5. 完整的多 Agent 调度系统。
6. 自动判断所有消息的语义归属。

P0 阶段允许由规则或上层 Agent 显式指定消息进入主线还是支线。

---

## 5. 核心概念

### 5.1 Session

Session 表示一次连续的会话空间。

一个 Session 对应一个明确的会话边界，例如：

- 一个 QQ 私聊窗口
- 一个群聊中的独立会话
- 一个 CLI 会话
- 一个绑定了 Workspace 的项目会话

每个 Session 必须拥有：

- 一个默认主线
- 零到多条支线
- 零到多个 Task

---

### 5.2 主线 Mainline

主线表示用户当前主要进行的对话。

主线主要承担：

- 用户与助手的连续交流
- 当前核心目标
- 最终结论
- 支线执行结果的回收
- 对用户可见的主要上下文

每个 Session 只能有一条默认主线。

主线不是一份不断覆盖的文本，而是一条持续追加的事件流。

---

### 5.3 支线 Branch

支线表示从主线中拆出的独立问题、探索过程或执行任务。

典型场景：

- 用户在当前讨论中临时提出另一个问题
- Agent 需要进行多轮搜索
- Agent 需要分析代码或文件
- Agent 需要执行一个较长任务
- Agent 同时尝试多个解决方案
- 群聊中出现与当前主线相关但不应直接打断主线的话题

支线必须记录其来源：

- 来源 Session
- 来源主线
- 来源消息
- 创建原因
- 支线目标

一条支线在同一时间只能属于一个 Session。

Branch 的语义接近 Git branch ref：它标识一条可持续推进、可审计和可恢复的结构化上下文，
而不是某一次执行。Task 或交互生成的是阶段性 Result；将 Result 发布到 Mainline，等价于让主线引用该次结果，
不等于完成、合并或关闭 Branch 本身。

因此必须区分：

- Branch：上下文引用和长期组织边界
- Task：一次有终态的执行
- Branch Result：某次执行或交互产生的不可变阶段结果
- Publication：Result 发布到 Mainline 的幂等事实
- Delivery：Mainline 结果投递到用户界面的结果

---

### 5.4 Append Event

所有会话变化都通过事件追加完成。

系统不直接修改已有消息，也不移动或覆盖历史记录。

事件类型包括：

- 用户消息
- 助手消息
- 系统消息
- 工具调用
- 工具结果
- 支线创建
- Task 创建
- Task 状态变化
- 支线结果
- 支线合并
- 消息修正
- 会话状态变化

如果历史内容需要修正，应追加一个 correction 事件，而不是覆盖原消息。

---

### 5.5 Task

Task 表示需要实际执行的工作单元。

例如：

- 搜索资料
- 分析仓库
- 生成文件
- 执行代码
- 调用外部 Agent
- 等待用户输入
- 汇总多个工具结果

Task 可以绑定：

- 一条支线
- 一个 Workspace
- 一个执行器
- 一组输入和输出产物

支线负责表达“为什么做”，Task 负责表达“具体做什么”。

---

## 6. 核心流程

### 6.1 消息进入系统

所有平台输入首先转换为统一的标准事件：

```text
Channel Input
    ↓
Normalized Event
    ↓
TranscriptStore
    ↓
Session Router
    ↓
Mainline / Branch
```

规范化事件至少保留：

- 原始平台
- 原始消息 ID
- Session ID
- 发送者身份
- 消息内容
- 消息段结构
- 表情、图片、回复、@ 等平台特性
- 接收时间
- 原始 payload
- 幂等键

原始 payload 应保留，避免规范化过程中丢失平台特有信息。

---

### 6.2 进入主线

以下消息默认进入主线：

1. 用户直接回复助手当前问题。
2. 用户继续当前核心话题。
3. 助手向用户输出最终结果。
4. 支线执行完成后的汇总结论。
5. 无法明确判断归属的普通对话消息。

主线是默认落点。

---

### 6.3 创建支线

满足以下任一条件时，可以创建支线：

1. 用户明确要求“另外处理一个问题”。
2. 新问题与当前主线相关，但需要独立上下文。
3. 任务需要多轮工具调用。
4. 任务预计产生大量中间内容。
5. 任务可以并行执行。
6. 用户明确要求后台执行。
7. Agent 判断任务过程不应污染主线。

创建支线时必须记录：

```text
branch_id
session_id
parent_mainline_id
source_event_id
title
goal
status
created_by
created_at
```

---

### 6.4 支线内执行

支线创建后，相关事件追加到该支线：

```text
Branch Created
    ↓
Task Created
    ↓
Task Started
    ↓
Tool Calls / Agent Output
    ↓
Task Completed
    ↓
Branch Result
```

工具调用过程、中间推理结果和执行日志默认不写入主线。

主线只保留必要的状态提示，例如：

```text
已创建支线：分析 nova-http 的 body parser 性能。
```

---

### 6.5 支线结果发布到主线

一次 Task 或支线交互产生阶段结果后，不将支线中的全部消息复制到主线，也不关闭支线。

系统应向主线追加一个 `branch_result` 事件，其中包含：

- 支线 ID
- 支线目标
- 执行状态
- 结果摘要
- 关键产物
- 关键引用
- 后续建议

示例：

```json
{
  "type": "branch_result",
  "branchId": "branch_123",
  "status": "completed",
  "summary": "已完成 body parser 性能分析，主要瓶颈位于重复 Buffer 拼接。",
  "artifacts": [],
  "nextActions": ["引入分段 Buffer 读取", "减少字符串中间态"]
}
```

主线中的结果事件只是对支线的引用和总结。

支线原始记录继续独立保存，并可承接后续消息、Task 和新版本 Result。

---

## 7. 状态模型

### 7.1 支线状态

```text
created
  ↓
active
  ↕
inactive
  ↓
archived
```

可恢复状态：

```text
blocked
```

状态说明：

- `created`：支线已创建，尚未开始执行
- `active`：正在讨论或执行
- `blocked`：等待用户、权限或外部条件
- `inactive`：当前没有进行中的执行，但仍可被后续消息或 Task 激活
- `archived`：不再参与默认上下文构建

`completed`、`failed`、`cancelled` 是 Task/Result 状态；“已发布”属于 Publication 状态，不应写入 Branch。
存量数据中的 Branch `completed`、`merged`、`failed`、`cancelled` 仅作为历史兼容状态读取，
在继续处理前迁移为 `inactive`，新代码不得再产生这些 Branch 状态。

---

### 7.2 Task 状态

```text
pending
running
blocked
completed
failed
cancelled
```

一条支线可以没有 Task。

例如，用户只是进入一个独立话题进行聊天时，可以只创建支线，不创建执行任务。

---

## 8. 上下文构建规则

### 8.1 构建主线上下文

主线上下文默认包含：

1. Session 基础信息
2. 主线最近消息
3. 当前活跃目标
4. 已合并的支线结果
5. 与当前消息高度相关的历史记录
6. 必要的 Workspace 信息

默认不包含：

- 支线全部执行日志
- 工具调用的原始输出
- 已归档支线的完整消息
- 无关 Task 的中间过程

---

### 8.2 构建支线上下文

支线上下文默认包含：

1. 支线目标
2. 创建支线的来源消息
3. 必要的主线背景摘要
4. 支线自身消息
5. 绑定 Task 的状态
6. Workspace 和产物信息

支线不应直接加载主线的全部历史。

创建支线时，应生成一份最小必要背景快照。

---

## 9. 数据关系

```text
Session
├── Mainline
│   ├── Event
│   ├── Event
│   └── Branch Result Reference
│
├── Branch A
│   ├── Event
│   ├── Task A
│   └── Branch Result
│
└── Branch B
    ├── Event
    ├── Task B
    └── Branch Result
```

推荐基础关系：

```text
Session 1 ── 1 Mainline
Session 1 ── N Branch
Branch  1 ── N Task
Line    1 ── N Event
Event   0 ── 1 Source Event
```

其中 Line 是主线和支线的统一抽象。

---

## 10. 功能需求

### FR-01 全量落库

系统接收到的用户消息、助手消息、系统事件和工具事件必须先落库，再进入后续处理流程。

落库失败时，不得继续执行会产生不可恢复副作用的 Task。

---

### FR-02 默认主线

创建 Session 时，系统必须自动创建默认主线。

所有未指定目标 Line 的事件默认进入主线。

---

### FR-03 创建支线

系统必须支持通过以下方式创建支线：

- 用户显式创建
- Agent 决策创建
- 系统规则创建
- Task 调度器创建

创建操作必须幂等。

同一个来源事件和同一个创建请求不得重复创建支线。

---

### FR-04 追加事件

主线和支线必须支持统一的 append 接口。

```text
appendEvent(lineId, event)
```

追加成功后，已有事件内容和顺序不得被修改。

---

### FR-05 创建 Task

系统必须支持在支线下创建 Task：

```text
createTask(branchId, taskDefinition)
```

Task 必须记录：

- 输入
- 执行器
- 状态
- 开始与结束时间
- 输出
- 错误
- 产物引用

---

### FR-06 发布支线结果

系统必须支持将支线结果追加回主线：

```text
publishBranchResult(branchId, mainlineId, resultId)
```

发布操作只追加结果引用，不复制完整支线历史，也不改变 Branch 生命周期。

同一版本的支线结果不得被重复发布。

---

### FR-07 恢复会话

Runtime 重启后，必须能够从数据库恢复：

- Session
- 主线
- 活跃支线
- 未完成 Task
- 尚未发布到主线的支线结果

---

### FR-08 查询与追踪

系统必须支持查询：

- 当前 Session 的主线
- 当前活跃支线
- 某条支线的来源消息
- 某个 Task 所属支线
- 某条结果来自哪个 Task
- 某个事件的完整调用链

---

## 11. 用户交互要求

用户默认只感知主线。

当支线创建或状态发生关键变化时，可向主线发送简短提示：

```text
已创建支线：调研现有 Skill Hub 方案。
```

```text
支线正在等待 GitHub 权限。
```

```text
支线已产生阶段结果，结果已发布到当前对话。
```

禁止将大量工具日志直接发送到主线。

用户可以通过命令查看支线：

```text
/branches
/branch <branch_id>
/branch cancel <branch_id>
/branch merge <branch_id>
/tasks
```

命令不是 P0 强依赖，但数据模型需要支持。

---

## 12. 异常处理

### 12.1 重复事件

通过以下字段进行幂等判断：

```text
channel
channel_account_id
source_event_id
event_type
```

重复事件不得重复写入或触发 Task。

---

### 12.2 Task 执行失败

Task 失败后：

1. 在支线追加失败事件。
2. 保存错误信息和已产生的产物。
3. Task 和 Result 标记为 `failed`；Branch 继续有活动时保持 `active`，否则回到 `inactive`。
4. 主线只收到简短结果，不写入完整错误日志。

---

### 12.3 支线长期未完成

支线超过配置时间未活动时，可以标记为 `inactive` 或自动归档。

自动归档不得删除历史事件。

---

### 12.4 主线继续产生新消息

支线执行期间，用户可以继续在主线对话。

支线不得锁定整个 Session。

支线产生阶段结果时，应基于支线目标生成独立结果，不应假设主线仍停留在创建支线时的状态。

---

## 13. 验收标准

### AC-01

创建一个新 Session 后，数据库中自动存在一条默认主线。

### AC-02

用户发送普通消息后，消息先落库，再进入主线处理。

### AC-03

系统可以从主线某条消息创建支线，并保留来源关系。

### AC-04

支线中的工具调用和中间结果不会自动进入主线。

### AC-05

支线产生阶段结果后，系统可以向主线追加一条结构化结果事件，同时保持支线可继续使用。

### AC-06

支线结果发布后，仍然可以查询完整的支线历史。

### AC-07

同一个支线结果重复执行 publish，不会在主线产生重复结果。

### AC-08

Runtime 重启后，未完成的支线和 Task 状态不会丢失。

### AC-09

主线和支线中的历史事件只能追加，不能被静默修改或覆盖。

### AC-10

可以从任意 Task 追踪到对应支线、来源消息和所属 Session。

---

## 14. P0 实施顺序

### 第一阶段：统一落库

1. 定义 Normalized Event。
2. 实现 TranscriptStore。
3. 实现事件幂等。
4. 保存原始平台 payload。

### 第二阶段：主线模型

1. 创建 Session。
2. 自动创建默认主线。
3. 实现统一 appendEvent。
4. ContextComposer 从主线读取上下文。

### 第三阶段：支线模型

1. 创建 Branch。
2. 记录来源消息和目标。
3. 为支线构建独立上下文。
4. 支持支线状态管理。

### 第四阶段：Task

1. 支线绑定 Task。
2. 记录 Task 生命周期。
3. 支持失败、取消和恢复。

### 第五阶段：结果回收

1. 生成 Branch Result。
2. 将结果引用追加回主线。
3. 防止重复发布。
4. 支持结果追踪。

### 第六阶段：投递闭环与恢复

1. 将上下文 Line、发布目标和 Channel 投递路由解耦。
2. 将 TaskExecutor 注册表注入 Runtime；启动时拒绝声明了但未注册的 executor。
3. Branch Result 必须先幂等发布到 Mainline，再对用户投递。
4. 持久化接收、运算、发布、投递各阶段状态，并支持重启恢复。
5. 同一 Session 串行提交 Mainline，同时允许不同 Branch 并行运算。
6. 使用 Outbox/Inbox 消除“已确认但未落库”和“已发送但状态未知”的窗口。

---

## 15. 核心设计原则

### 原则一：先落库，后处理

任何进入 Runtime 的信息都应先成为可恢复的标准事件。

### 原则二：主线默认，支线按需

普通对话默认进入主线，只有独立且有价值的问题才创建支线。

### 原则三：支线隔离过程，主线接收结果

执行过程保存在支线，主线只接收对用户有价值的状态和结果。

### 原则四：只追加，不覆盖

消息、状态变化和修正均以新事件表达，保证完整追踪和恢复能力。

### 原则五：Branch 表达上下文，Task 表达执行

支线负责组织问题和讨论，Task 负责管理实际执行工作。

### 原则六：Mainline 是唯一用户发布面

Branch 隔离运算过程；所有用户可见结果先形成可审计的 Result 和 Publication，再由 Mainline 投递。
结果发布不关闭 Branch，投递失败也不回滚已经形成的语义结果。

---

## 16. 一句话定义

> Synapse Runtime 将每个会话组织为一条持续发展的主线和若干可持续跟进的结构化支线；所有信息先规范化落库，通过 append-only 事件记录变化，Task 在支线中产生阶段结果，结果经幂等发布进入主线并投递给用户，而支线继续保留上下文和审计历史。
