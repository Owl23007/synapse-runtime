# 路线图

Synapse Runtime 的稳定产品目标是 **1.0：可持续运行、可审计、可扩展、可升级的本地优先 DAG Agent Runtime**。0.1 就确立核心架构与完整使用体验，后续版本逐步扩大适用场景，不把基本质量留到 1.0 才补齐。

当前实施基线为 0.1 正式版 PRD，配套代码审计与发布验收清单。本轮已完成审计和规划，正式版开发尚未开始。旧工件 PRD 的“完成”表示基础链路实现完成，不表示 0.1 已正式发布。

## 从 0.1 到 1.0

以下按退出条件推进，不以日期或功能数量代替质量。0.1 工作包已具体拆分；后续版本在前一阶段验收后形成独立 PRD，避免将未经验证的需求当成既定实现任务。

| 阶段              | 产品结果                                       | 必须交付                                                                                                  | 退出条件                                                                             |
| ----------------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 0.1 首个正式交付  | 维护者能部署、执行、观察、检查、交付和排障     | 稳定 Run/Trace、DAG 来源、完整工具与交付事件、可靠查询/SSE、WebUI、恢复/安全/数据维护、发布文档           | PR-01～09、A01～A22、四类证据与 24 h 候选运行全部通过                                |
| 0.2～0.3 日常运行 | 实际使用积累不降低可用性，长会话与故障可处理   | 基于使用反馈修复体验；完善运行取消和安全续作；容量/保留策略、统一预算与诊断；提升配置应用失败后的恢复能力 | 代表部署连续运行 7 天，过载/取消/断线/备份恢复有验证，无重复交付和无法解释的状态     |
| 0.4～0.6 可控扩展 | 新模型、频道和工具能遵守同一契约接入           | Provider/Adapter/Tool 扩展契约、能力声明、契约测试与升级规则；按实际需求接入后台任务或审批                | 至少两种不同能力的频道和模型配置通过兼容套件；每个扩展复用 Run、权限、隔离和回执机制 |
| 0.7～0.9 稳定化   | 可重复安装、升级和维护，候选版本有明确兼容边界 | 配置/API/事件版本策略、迁移与回滚矩阵、故障演练、支持矩阵、发布产物与回归自动化、缺陷收敛                 | 从受支持旧版本升级与恢复均验证，公开稳定面冻结，完成 1.0 候选验证                    |
| 1.0 稳定产品      | 面向声明的部署规模可持续使用与维护             | 稳定 API 与扩展边界、支持和弃用政策、操作手册、可重复发布与问题定位流程                                   | 满足下述 1.0 完成定义并正式放行                                                      |

多 Agent、分布式调度、通用图编辑器、插件市场、向量数据库与多租户不自动成为 1.0 的必选功能。它们只有在目标用户需求明确、能够复用安全与恢复契约时才独立立项。1.0 的完整性来自既定产品范围可长期使用，而不是覆盖所有 Agent 平台功能。

## 1.0 完成定义

| 维度         | 稳定产品的要求                                                               | 从 0.1 开始建立的基础                      |
| ------------ | ---------------------------------------------------------------------------- | ------------------------------------------ |
| 完整使用流程 | 新用户按文档安装、连接、执行和排障，无需读实现代码；真实交付可复核           | 首次使用、Run Detail、Explorer 与部署指南  |
| 兼容性       | 明确列出稳定的 API、配置、事件和扩展接口；补丁版本不破坏承诺，弃用有迁移说明 | 协议版本、迁移记录、契约测试与边界检查     |
| 数据可靠性   | 已确认结果不丢失；未知副作用不自动重复；备份恢复与升级可重复                 | 写前检查点、幂等、事件投影、回执与完整备份 |
| 可运维性     | 声明容量、支持平台、保留策略与故障处理步骤；健康检查反映真实就绪状态         | 有界资源、运行诊断、数据维护与发布门禁     |
| 扩展能力     | 新 Provider/Adapter/Tool 可按文档和契约测试接入，不修改 Runtime 核心循环     | 显式组装、模块边界、权限与 Trace 契约      |
| 安全与隐私   | 声明管理员信任边界与数据保留方式；不存在未关闭的严重越权、泄密或执行隔离问题 | 来源绑定、凭据脱敏、受保护查询与容器约束   |
| 发布质量     | 每个支持环境有自动回归与安装升级验证；变更日志、校验信息和回滚说明齐备       | 可重复构建、独立验收证据、候选版本流程     |

1.0 候选期至少完成一个代表性部署的 30 天持续运行观察，记录请求量、故障、恢复和资源趋势；至少演练进程崩溃、磁盘不足、外部服务超时与备份恢复。吞吐和延迟目标以 0.1/0.2 实测及声明的容量范围为依据，在候选期前冻结。没有代表性部署证据时，不以单元测试通过替代稳定性验收。

## 当前执行顺序

先完成运行契约、SQLite 与全链路采集，再完成恢复约束、只读 API 与 SSE，随后完成 WebUI 和数据运维，最后做真实联调及发布候选验收。详细依赖和 39–58 人日的初步估算见 0.1 实施工作包。估算不含外部账号等待，且应在每个工作包退出后重估。

## 状态流程

`规划中（WIP）` → `下一步计划` → `进行中` → `完成（本迭代）` → `归档`

完成的 PRD 会保留在“完成（本迭代）”中，以便在当前迭代复盘；确认无需继续维护后，再移入 `docs/prd/archive`。

## 维护方式

在 PRD 顶部使用 frontmatter 指定其阶段，并通过任务清单维护完成进度：

```yaml
---
status: in-progress
progress: 40
---
```

可用状态为 `wip`、`next`、`in-progress`、`completed` 和 `archived`。未标注状态的 PRD 默认进入“规划中（WIP）”；归档目录中的文档始终显示在“归档”。

## 计划维护规则

- 功能只有在对应退出条件与证据齐备后才勾选完成，文档写完不增加实现进度
- 新增范围必须说明目标用户、版本归属和验收，不挤占未完成的 0.1 P0
- 每次阶段验收更新实现状态、风险与实际耗时，发布前单独检查门禁
- 0.x 允许有说明的契约调整，但必须给出迁移和兼容边界；1.0 后遵守公开稳定面承诺
